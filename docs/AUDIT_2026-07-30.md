## 2. Critical finding — the platform had two contradictory sources of truth

### The defect

The platform contained **two independent transaction simulators**:

1. `backend/app/warehouse/generator/` → raw parquet corpus (2.73 M rows, 50
   columns). No KPI is asserted; success rate, growth and seasonality are
   *emergent* from per-transaction outcomes. Feeds Analytics, Products, the ML
   pipeline, and `/intel/*`.
2. `generate_enterprise.py::Ledger` → sampled ~10 k rows/day and then
   **reconciled them to a hand-authored KPI series**:

   ```python
   sr = k.value("Success Rate (%)", d)      # asserted, not measured
   n_success = int(round(N * sr / 100))     # transactions built to match it
   ```

   It rolled those rows into `enterprise_data/master/analytics/*.csv`, read by
   Ecosystem, Evolution, the executive surfaces and ~30 other modules.

The second has the causality backwards — the KPI produced the transactions
rather than the transactions producing the KPI — and its KPI engine had no
knowledge of the 83 incidents the warehouse simulates.

### Measured impact

Agreement between the two sources on the **same 206 business days**:

| KPI | Correlation | Mean drift | Worst day |
|---|---|---|---|
| Success rate | **+0.1975** | 0.61 pp | 2026-01-28: **4.38 pp** |
| Attempts / volume | **+0.2289** | 4,409 txns | 2026-06-20 |
| Average ticket | **−0.3866** | ₹176.93 | 2026-01-11 |

Average ticket correlated *negatively*: the published series moved opposite to
the transactions it claimed to summarise.

Concretely, on **2026-01-28** the Analytics page reported **95.17%** success
(a real incident) while the Ecosystem page reported **99.55%** (a good day).
Same company, same day, same product, two answers — and an incident invisible on
the surface an executive uses to spot incidents.

A third surface carried the same defect: `master/upi_kpis_month.xlsx`, the
source behind `/executive/trends`, `/executive/kpis`, week-over-week,
month-over-month and report trend rows, correlated **+0.197** with the corpus.

### The fix

The cubes and the workbook are now **projections of the corpus**, not a parallel
invention. New modules:

- `backend/app/warehouse/projection.py` — 11 cubes as SQL aggregates over the
  raw corpus, plus `project_kpi_workbook()` for the workbook.
- `backend/app/warehouse/project_cubes.py` — CLI (`--check` reconciles without
  writing).
- `backend/app/warehouse/reconcile.py` — correlation/drift report per KPI.

```bash
python -m app.warehouse.project_cubes          # rebuild from the corpus
python -m app.warehouse.project_cubes --check  # reconcile, exit 1 on drift
```

### Result

| KPI | Before | After |
|---|---|---|
| Success rate | +0.1975 | **+1.0000** (drift 0.0025 pp) |
| Attempts | +0.2289 | **+1.0000** (drift 0.0000) |
| Average ticket | −0.3866 | **+1.0000** (drift 0.0024) |
| Volume (M/day) | +0.2289 | **+1.0000** (drift 0.0237) |

Deliberate restraint: only rows a transaction can answer were rewritten.
`Customer Complaints`, `Fraud Alerts`, `Merchant Adoption`, `Risk Score` and
`Settlement Success` are owned by other subsystems and were left untouched —
fabricating them from payment rows would replace an honest external number with
an invented one. A test asserts they stay out of the projection.

### Secondary improvements found while projecting

- **`archetype` is now evidence-derived.** It used to be a label the KPI engine
  stamped on a day in advance; it is now read back out of the corpus, so a day
  labelled "Incident-affected" provably has a depressed success rate. A test
  enforces the label and the numbers cannot contradict each other.
- **Risk declines were being silently dropped.** The cube schema had
  technical/business/pending columns but no risk column, so 1,891 risk-bucket
  failures vanished and the decline splits never summed to 100%. A
  `risk_decline_pct` column was appended (additive — consumers use
  `csv.DictReader`).
- **`merchant_daily` bounded.** An unbounded projection is 292,638 rows (95× the
  previous cube) held permanently in memory by the ecosystem loader. Capped to
  the top 50 merchants by window volume, with a stable panel so merchants do not
  flicker between days.
- **Projection made deterministic.** The first draft used DuckDB `any_value()`,
  which returns whichever row the parallel scan reached first. A test now
  asserts two runs over an unchanged corpus produce byte-identical cubes.

## 3. The AI answer quality defect

The question *"Why did transaction value change?"* returned **10% confidence**
and "the available dataset does not contain direct information", while the
platform held a verified root-cause breakdown. Traced end-to-end:

**Cause 1 — vocabulary split (fixed).** The query classifier canonicalises to
`Transaction Value (₹ Cr)`; the warehouse labels the same measure
`Settled value`. The model received evidence about "Settled value" for a
question about "transaction value" and — correctly, on the words alone —
reported the evidence covered a *different metric*, then declined. Its own
stated limitation:

> "The evidence does not provide a direct explanation for the change in
> 'transaction value'; it only provides root causes for 'Settled value'."

Fixed by adding `aliases` to `KPI_META` and a `kpi_label()` helper that names a
metric the way the question did: evidence now reads **"Settled value
(transaction value)"**. Applied to both trend and root-cause evidence.

**Cause 2 — the numeric guardrail rejected its own arithmetic (fixed).** With
the label fixed, the model *did* use the evidence — and was then rejected for
quoting `8,047,670`, which is exactly `28,338,086 − 20,290,416`, the difference
between two cited figures. The most useful sentence an analyst can write ("value
fell **by** X") was the one most likely to be blocked.

The validator now accepts a figure that is elementary arithmetic over evidence
values — **but only when the answer states both operands**. That restriction is
essential and was learned the hard way: an unrestricted version accepted the
invented figure `987654`, because *n* evidence numbers generate *n²* sums and
differences that blanket the number line. Requiring the answer to show its work
keeps the claim checkable by a reader, which is the property the gate actually
protects. Verified: the derived delta passes, `987654` and `999999` are still
rejected, and all 71 copilot tests pass unchanged.

**Cause 3 — model capability (not fixed, recommendation below).** With both
defects fixed the validator returns `verified` with no rejections, the
root-cause evidence is correctly labelled and leads the prompt — and the
configured local model (`ollama / gemma4:e4b`) still declines to synthesise from
it. This is a model-capability limit, not a data or plumbing defect. See §6.

## 3a. Comparison questions answered the wrong question, silently

Reported after the first pass: *"compare upi autopay and upi lite in the month of
may 2026"* returned 10% confidence. Three independent defects, each of which
failed **silently** — the platform produced a confident-looking answer about the
wrong products over the wrong period:

1. **No pattern matched a whole month.** `_time_range()` handled ISO ranges,
   month+day ranges and relative windows, but nothing matched "May 2026" or
   "in the month of May". It fell through to `None` and the engine applied its
   default trailing 30 days — so the answer covered **2026-06-30 to 2026-07-29**
   for a question about **May**.
2. **Only the first product resolved.** `_match_product()` returned inside its
   loop on the first hit, so a two-product question resolved to `UPI_AUTOPAY`
   alone. Half the request was dropped with no warning.
3. **No comparison path existed.** The engine computed one aggregate series over
   one filter. Even with both products in the slice it would have emitted a
   single *blended* trend, which cannot answer "compare A and B" however capable
   the reading model is.

**Fixes:**
- `classifier.py` — `_MONTH_YEAR` / `_MONTH_ONLY` patterns and a `month` time
  range kind, matched *after* the day-bearing patterns so "July 1 to July 20"
  is still a day range. Labels render the full month name.
- `_slice.py` — `_whole_month()` resolves a calendar month against the corpus: a
  month with no year picks the most recent one with data, a partial month is
  labelled `partial`, and a month outside the corpus is labelled
  `out_of_range` rather than silently answering about another period.
- `_slice.py` — `_match_product` → `match_products`, returning every named
  product in order. One product stays a scalar filter; two or more become a list,
  which `Filters.where()` already renders as `IN (?, ?)`.
- `analytics.py` (engine) — `_comparison_evidence()` emits one measured block per
  entity plus an explicit head-to-head verdict (leader, laggard, gap, ratio,
  best success rate). Triggered by two or more named entities of the same kind,
  not by `comparison` intent alone, since "how did AutoPay and Lite do in May"
  classifies as a question and still needs both sides.

**Result** (live):

| | Before | After |
|---|---|---|
| Confidence | 10% | **100%** |
| Window | last 30 days (Jun 30–Jul 29) | **May 2026** (May 1–31) |
| Products in slice | `UPI_AUTOPAY` | **`['UPI_AUTOPAY', 'UPI_LITE']`** |
| Comparison evidence | none | **3 items** (2 sides + verdict) |

The answer is now a real side-by-side: UPI Lite 59,798 attempts / ₹5.56 M
settled at 99.79% success, versus UPI AutoPay 13,741 attempts / ₹29.30 M at
96.44% — coherent with the products' economics (Lite is high-frequency
low-ticket; AutoPay is mandate-driven high-ticket).

18 regression tests in `backend/tests/unit/test_comparison_queries.py`, including
guards that the existing day-range and relative patterns still win.

## 3b. Round two — the data foundation, measured against the brief

A follow-up brief asked for a complete redesign of the data foundation:
transaction-level fact table, full NPCI product coverage, mandate lifecycle
event sequences, persistent evolving entities, learned forecasting, and removal
of precomputed aggregates.

**Measured first.** Most of it already existed and did not need redesigning:

| Requirement | Measured state |
|---|---|
| Transaction-level fact table | 2.73 M rows x 50 columns, one row per attempt |
| Full product coverage | All 12 products present **including UPI Circle** |
| Intent / Collect / QR | Present as payment types (P2M-Intent, P2P-Collect, P2M-QR-Static/Dynamic) |
| Mandate lifecycle | All 12 event types: CREATED, MODIFIED, PAUSED, RESUMED, EXECUTED, RETRY, FAILED, EXPIRED, CANCELLED, REVOKED, MERCHANT_INITIATED, PRE_DEBIT_NOTIFICATION |
| Merchant lifecycle | 371 merchants entered after day 20; 20 went inactive |
| Customer lifecycle | 22,996 acquired later; 10,496 churned; monthly actives 52.6k -> 66.2k |
| Products / Ecosystem / MCC Explorer | Already read `/intel/*` (warehouse SQL), not cubes |

Rewriting a generator that already produces this would have destroyed working,
well-calibrated code. **The genuine gap was the last precomputed aggregates.**

### forecasts.csv was template logic, and ~38 modules read it

`generate_enterprise.py::build_forecasts(trends)` computed:

```python
forecast_next = last_7d + (last_7d - prev_7d) / 7
```

A straight-line extrapolation of a moving average. No confidence, no validation,
no notion of whether the series was forecastable. The forecasting engine, the
copilot and its planner, report generation, product growth and scenarios, the
Enterprise Brain, prompt builders and the tool layer all inherited those
properties.

`MLPipeline` already did the real thing on the raw corpus. New module
`backend/app/warehouse/forecast_projection.py` writes its output into the two
cubes the platform already reads, so every consumer gets a learned forecast with
no consumer-side change:

| Series | Model | Backtest MAPE | Skill vs naive | Confidence |
|---|---|---|---|---|
| total::sample_txns | HistGradientBoosting | 3.77% | +62.6% | 86.4 high |
| total::sample_value_inr | HistGradientBoosting | 6.89% | +52.5% | 79.5 high |
| total::avg_ticket_inr | HistGradientBoosting | 5.97% | +24.8% | 78.5 high |
| total::success_rate | HistGradientBoosting | 0.38% | **-29.1%** | 74.4 **moderate** |

Each row now carries the model, out-of-sample error, skill against a
seasonal-naive baseline, observation count, top driver with its importance, a
business explanation, the primary risk and a recommended action.
`forecast_forward.csv` carries real 80% prediction intervals per horizon day.

**Honesty rule enforced:** a series the pipeline declines to model is written
with empty forecast fields and a stated reason, never a fabricated number. A
test asserts an unavailable row cannot also quote a value.

### A calibration bug this surfaced

`total::success_rate` backtests at 0.38% error but is **worse than seasonal-naive
by 29%** — the series sits near 99% all year, so "assume next week looks like
this one" wins. It was scoring 74.4 and being labelled **high confidence**, whose
interpretation text asserts the model *"beat a seasonal-naive baseline"*. That
statement was simply false, in executive-facing text.

`insight.confidence()` now caps the band at moderate when skill is negative,
exposes `beat_naive_baseline`, and states what actually happened. Four unit tests
cover it, including one that the false claim can never be printed.

### Product cubes projected

`product_lifecycle` and `feature_adoption` are now monthly aggregates of the
corpus. `lifecycle_stage` is computed from measured share and momentum rather
than written by hand, so a product that stops growing stops being called
"Growth". Tests assert the label agrees with the growth number and that monthly
market shares sum to 100%.

## 4. What was found to be sound

Reporting this matters as much as reporting defects — several areas did not need
the changes the brief anticipated.

**The transaction simulator is genuinely high quality.** The brief asked for it
to be redesigned to produce realistic behaviour. Measured, it already does:

- lag-1 autocorrelation **0.777**, lag-7 **0.647** (real persistence, not noise)
- day-over-day σ 11.6%, range 2.47× — realistic for a payments network
- incidents visible as success-rate dips (2026-01-23 → 95.05%)
- festivals and campaigns visible as volume spikes
- retries, reversals, refunds, chargebacks, mandate execution with balance
  failures clustered in the pre-salary trough, AR(1) bank/PSP reliability drift,
  Poisson arrivals, per-product intraday hour profiles, round-number ticket
  clustering

Rewriting it would have destroyed working, well-calibrated code. **The
unrealistic day-wise data the brief describes was the *other* generator** — the
one now removed from the truth path.

**The ML pipeline performs genuine EDA from raw transactions.** Verified live on
`value_inr`:

- 42-fold walk-forward backtest, MAPE **6.89%** vs seasonal-naive **14.49%** →
  **52.5% skill**
- 80% prediction-interval coverage measured at **83.3%** (well calibrated)
- Mann-Kendall trend test, change-point detection with t-statistics,
  stationarity tests, weekly seasonality decomposition
- confidence decomposed into components *and* weights, exposed in the response
- feature importances real (`spend_multiplier`, `value_inr_lag_7`, …)
- data path confirmed: `build_daily_frame` → `analytics.daily_series` → SQL over
  raw parquet. No precomputed aggregate anywhere in it.

**410 MB of day-wise CSVs are written and never read.** `generate_enterprise.py`
writes `enterprise_data/day_*/ledger/txns_day_*.csv` (2.06 M rows). The only
reference in the entire backend is `reader.py:135`, which explicitly skips them:
`dirs.remove("ledger")  # raw ledger is never read here`. Recommendation in §6.

## 6. Recommendations, in priority order

1. **Upgrade the answering model.** `gemma4:e4b` declines to synthesise from
   correctly-labelled, leading evidence. The retrieval, routing, evidence and
   validation layers are all working; the narrator is the weak link. Try a
   larger local model or a hosted one and re-run
   *"Why did transaction value change?"* as the acceptance test.
2. **Delete the unread day-wise ledger CSVs** (410 MB, zero readers), or make
   `--ledger-size 0` the default in `generate_enterprise.py`. They are pure
   repository weight.
3. **Project the remaining derived cubes.** `forecasts`, `forecast_validation`,
   `storylines`, `bi_findings`, `decision_tracking`, `product_lifecycle` and the
   `*_evolution` set are still produced by the old generator. `forecasts` is
   read by ~38 modules and `trends` by ~30, so these carry real weight. `trends`
   is already projected; the rest should follow the same pattern.
4. **Retire `generate_enterprise.py::Ledger` entirely.** With the cubes and
   workbook projected, its only remaining job is producing files nobody reads.
   Removing it eliminates the second simulator at the source rather than
   downstream.
5. **Wire `--check` into CI.** The reconciliation guard only prevents regression
   if something runs it. It exits non-zero on drift and is already a test.
6. **Audit the seven admin pages never verified by click-through** (Brain,
   Graph, Connectors, Sync, Runtime, Jobs, Diagnostics). All render live data,
   but only the API-level subsystem report has been checked — the same gap that
   let the earlier ML/LLM page mismatch hide.
7. **Reconsider the corpus failure rate.** 0.95% overall failure (26,030 of
   2.73 M) is thin for failure-mode analytics: risk declines total 1,891 across
   206 days, which is sparse for per-bank or per-MCC breakdowns. Realistic for
   *technical* declines, but it starves the failure-analysis surfaces.
